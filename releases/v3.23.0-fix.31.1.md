# v3.23.0-fix.31.1

> [!NOTE]
> v3.23.0-fix.31.1 turns on **zero-downtime updates for systemd nodes**, the half of HotSwap that 31.0 shipped dormant. Alongside it, the provider now **backs off destinations that keep denying contracts**, **picks dialers by measured health** instead of a fixed priority, and **launches proxies in order of what each identity actually earns**, using the history 31.0 started collecting. It also fixes a set of control-plane and hardening bugs: a descriptor double close in `urnet-tools`, a `gogc` value that could switch garbage collection off, a persisted `metrics on` that never survived a restart, and a `history` command that failed on every invocation.
>
> Rebuild and redeploy provider nodes, and update `urnet-tools` and `urnet-docker`. **On a 31.0 node, run `urnet-tools self-update` before `urnet-tools update`** to get the systemd migration on this upgrade. See [Upgrade Notes](#upgrade-notes).

## 1. Overview & Highlights

- **HotSwap on systemd**: `urnet-tools update` migrates the provider unit from `Type=simple` to `Type=notify` when the binary it installs signals readiness at startup. From the next update on, the provider hands over in place instead of restarting. The unit is kept paired with the binary it runs, so a downgrade or rollback puts it back to `Type=simple` before an older binary can hang its own start.
- **Contract denial backoff**: a destination that keeps refusing contracts is retried on a growing schedule, from 15 seconds up to 5 minutes, instead of on the fixed retry interval. The wait drops back the moment a contract succeeds.
- **Health-aware dialer selection**: dialers are weighted by success rate, latency and error streak, serial dialers are ordered by that health, and the parallel probe batch halves on a healthy network.
- **Earnings launch ranking**: warm identities launch first, proven earners join the file list, and within a group the bigger earner dials first. New addresses still get tried.
- **Metrics that survive a restart**: `urnet-tools set metrics on` works without `URNETWORK_METRICS`, on loopback, and a persisted `on` is applied at boot.
- **`gogc off` always restores the default**: before, `OFF` in some casings switched garbage collection off.
- **Hardening**: a `urnet-tools` file descriptor double close is fixed, and every file root writes into a provider-owned directory is written without following symlinks.

## 2. HotSwap on systemd

### Why 31.0 shipped it dormant

HotSwap hands the unit's `MainPID` to the new process, which needs `NOTIFY_SOCKET`, and systemd only provides that to a `Type=notify` unit. The installer writes `Type=simple`, so on every systemd node 31.0 declined HotSwap and updated with a restart.

`Type=notify` was held back for two reasons. The first was fixed inside 31.0: the provider used to send `READY=1` only after a proxy authenticated, which could take hours against a rate-limited API, and it now sends it at the startup barrier, as soon as it is self-managing (#543). The second is structural and is why the installer still writes `Type=simple` (#546). The unit comes from the installer and the binary from a release, and a `Type=notify` unit paired with a binary that never sends `READY=1` fails every start. A fresh install that lands an older release, or a rollback, creates exactly that pairing.

### What 31.1 does

The migration lives in `urnet-tools update`, the one place that knows which binary is about to run under the unit, and keeps the two paired:

| The update installs | The unit becomes |
|---|---|
| v3.23.0-fix.31.0 or newer (sends `READY=1` at startup) | `Type=notify`, with `NotifyAccess=all` added if absent |
| Anything older | `Type=simple` |
| A binary whose version cannot be read | `Type=simple` |

A HotSwap rollback that restores a binary older than 31.0 also puts the unit back to `Type=simple` before that binary can start under it. A wrong demotion costs one update's worth of zero-downtime. A wrong promotion fails every start. The rules always pick the first.

The update that migrates still restarts the provider, because the running process was started under the old unit without `NOTIFY_SOCKET` and cannot complete a handoff. The next update is the first that hot swaps.

A migrating update prints:

```
swapped <staged> -> ~/.local/share/urnetwork-provider/bin/urnetwork
backed up unit file ~/.config/systemd/user/urnetwork.service -> ~/.config/systemd/user/urnetwork.service.bak
migrated ~/.config/systemd/user/urnetwork.service from Type=simple to Type=notify
daemon-reload completed after unit migration
unit migrated to Type=notify; using standard restart (running process lacks NOTIFY_SOCKET)
verified <provider> running v3.23.0-fix.31.1 (pid <pid>; running image <path> matches)
```

and the following update prints:

```
triggered zero-downtime HotSwap handoff (SIGUSR2 sent to PID <pid>)
```

> [!TIP]
> Check which side of the migration a node is on with
> `systemctl --user show -p Type urnetwork.service`. `notify` means the next
> update can hot swap; `simple` means the next update migrates.

> [!NOTE]
> The migration is never fatal. If the unit type cannot be read, the unit file cannot be resolved, or the write fails, `update` prints `unit migration note: <reason>` and restarts the provider exactly as 31.0 did.
>
> Re-running `Provider_Install_Linux.sh` writes a fresh `Type=simple` unit, and a fresh install starts on `Type=simple` too. In both cases the next `urnet-tools update` migrates it again.

### Written as root, safely

`urnet-tools update` can run as root while the unit lives in the provider user's `~/.config/systemd/user`, a directory that user controls. The unit's temp file and `.bak` are written with `O_NOFOLLOW`, so a symlink planted at either path cannot redirect a root write. A unit file that is itself a symlink is refused rather than read, so its target can never be copied into the world-readable backup. Files root creates there are handed to the directory's owner, so the provider user keeps ownership of their own unit.

### Declines say why, and are counted

Every HotSwap decline point now prints what went wrong and what happens next, for example:

```
hotswap trigger unavailable (zero-downtime hotswap unavailable: the provider's systemd unit is Type=simple (as Provider_Install_Linux.sh writes it); `urnet-tools update` migrates it to Type=notify, after which updates can hot swap. This update uses a service restart); falling back to service restart
```

Outcomes are counted in `~/.urnetwork/.hotswap_declines.json` and served on `/metrics`:

```
urnet_hotswap_outcomes_total{reason="success"} 3
urnet_hotswap_outcomes_total{reason="unit_not_notify"} 1
```

| `reason` | Meaning |
|---|---|
| `success` | The new version was verified running after a handoff |
| `version_old` | The running provider predates HotSwap |
| `unit_not_notify` | The unit is still `Type=simple` |
| `unit_query_error` | The unit type could not be read |
| `windows` | HotSwap is not available on Windows yet |
| `no_pid`, `trigger_pid`, `trigger_find`, `trigger_signal` | The running process could not be found or signalled |
| `takeover_failed` | The candidate did not confirm takeover in time. The binary is rolled back unless ownership had already transferred |
| `other` | Any other decline |

## 3. Contract Denial Backoff

When a destination refuses a contract, the send path used to ask again on the fixed contract retry interval, however many times it had already been refused. Each destination now carries its own backoff:

| Consecutive denials | Wait before the next request |
|---|---|
| 1 | none |
| 2 | 15s |
| 3 | 30s |
| 4 | 60s |
| 5 | 120s |
| 6 | 240s |
| 7 or more | 5 minutes |

- The wait is recomputed before every retry, from the configured retry interval, the degraded-backend backoff and the destination's current backoff, so it rises as refusals arrive and drops straight back once a contract succeeds.
- A successful contract clears the destination. State with no new denial expires after the current backoff plus two minutes, so the longer tiers are actually reachable.
- A frame carrying several contract errors counts as one refusal.

Denials are logged as before, one `⛔ [contract] denied = <reason> destination=<id>` line each.

## 4. Dialer Selection

Connections to the platform choose among several dialers: the normal path, extenders and pluggable transports. 31.1 uses what each dialer has actually done.

- **Composite weight**: a dialer's success ratio, multiplied by a latency factor (a moving average against a 500 ms baseline, from a 1.2x boost down to a 0.3x penalty) and by a halving penalty per consecutive error, floored at the dialer's minimum weight.
- **Serial ordering**: dialers tried one at a time are ordered by priority, then success rate, then the most recent success. Each dialer's health is read once, under its lock, before sorting.
- **Adaptive parallel batch**: each client strategy, and a provider runs one per proxy, keeps its own 10-second window of dial outcomes. When more than 80% succeed, the batch halves. Otherwise it uses the configured `ParallelBlockSize`, and it never exceeds it.

`[net]` debug lines for a dialer now include its average latency, for example `success=12 error=1 avg=184ms`.

## 5. Earnings Launch Ranking (#601)

31.0 started recording what each proxy identity earns, as billable bytes with a one-week half-life, and deliberately did not act on it. 31.1 uses it to order launches:

1. **Warmth.** A proxy holding a valid client JWT dials before one that must mint a new identity. Minting is rate-limited, so a rich but cold proxy jumping the queue would spend a scarce mint slot and stall warm identities that could have dialled straight through. A warm URL-sourced proxy therefore launches before a cold file proxy.
2. **Trusted provenance.** Within a warmth tier, file and internal proxies launch first. A URL-sourced proxy joins them once its decayed earnings pass 64 MiB, at which point it is a known earner rather than an unproven address off a public list. Promoted proxies also skip the deferral that holds URL proxies back until file-proxy warmup completes.
3. **Earnings.** Within a tier and group, the bigger earner dials first.

Among cold proxies, one unproven URL-sourced proxy is interleaved after every five trusted ones, so a node that restarts often still tries new addresses and lets them build a history.

The startup log reports what the history contributed:

```
💰 [startup] earnings ranking: 588 of 812 proxies have earnings history, 34 URL-sourced promoted to launch with the file list, top earner 203.0.113.9:1080 at 4.1 GB
```

A node with no history orders by warmth and source only and says so:

```
💰 [startup] earnings ranking: no history yet, launching by warmth and source only
```

> [!NOTE]
> The ranking only reorders launches. It never admits, evicts or rejects a proxy, and a node with no history behaves as 31.0 did.

## 6. Control Plane & Metrics

### `urnet-tools history` works

The command, added in 31.0, decoded the provider's audit timestamps as integers while the provider sends RFC 3339 strings, so every invocation failed to parse. It now lists the provider's command audit ring, with `--limit` and `--cursor` for paging.

### `metrics on` without `URNETWORK_METRICS`, and after a restart

In 31.0 `urnet-tools set metrics on` required `URNETWORK_METRICS` to be set when the provider started. Now:

- With `URNETWORK_METRICS` unset, the listener binds the first free port in `127.0.0.1:9100` to `127.0.0.1:9103` and serves on that listener directly, so the port cannot be taken between probing and binding. If none is free, `set` returns the error instead of reporting success.
- A persisted `metrics on` is applied at boot. Before, the value was saved but nothing started the listener after a restart, so the setting quietly disappeared.
- With `URNETWORK_METRICS` set, behavior is unchanged: that address is used, and the provider starts the listener from it at boot.

```
[metrics] started Prometheus /metrics on 127.0.0.1:9100
```

> [!CAUTION]
> An automatically chosen port is always loopback. To scrape remotely, set `URNETWORK_METRICS` to an explicit address such as a Tailscale IP. Never use a bare `:9100`, which binds every interface and publishes per-proxy detail to the internet.

### `gogc off` always restores the default

`off` is the clear value for every tuning key. The CLI turned a lowercase `off` into a clear, but `OFF` or `Off` passed validation and reached the provider as a set, where it switched garbage collection off on a live node. `off` in any casing now restores the default, and the CLI and startup checks are case-insensitive.

```
⚙️ [control] applied gogc=100 (off restores the default)
```

### Human-friendly byte counts (#610)

`urnet-tools set gomemlimit` accepts the suffixes people actually type: `1536M`, `2G`, `512MB`, `1g`, `2tib` and spaced values like `1536 mb`, alongside the original `MiB` and `GiB` forms. Errors show valid examples instead of a raw parse error.

## 7. Security & Hardening

- **`urnet-tools` closed a descriptor it no longer owned.** `writeStateFile` wrapped its file descriptor in an `*os.File` and also closed the raw descriptor. The `*os.File`'s finalizer later closed the same number again, after the kernel had handed it to another open file, which could silently close whatever `urnet-tools` opened next. It surfaced as intermittent "bad file descriptor" test failures.
- **Root writes into provider-owned directories no longer follow symlinks.** The HotSwap counter file and the systemd unit's temp and backup files go through the same `O_NOFOLLOW` path as other state writes, a symlinked unit file is refused, and new files are handed to the directory's owner.
- **Automatically chosen metrics ports bind loopback only.**
- **CFAA blocklist synchronized with upstream (#609).**

## Upgrade Notes

> [!IMPORTANT]
> **On a 31.0 node, run `urnet-tools self-update` and then `urnet-tools update`.**
>
> `urnet-tools update` updates providers with the `urnet-tools` binary already installed, and refreshes the tool itself only at the end. The unit migration is new in 31.1, so a 31.0 tool running the upgrade does not know to migrate: the provider reaches 31.1 with a restart, exactly as in 31.0, and the migration happens on the next release. Running `self-update` first puts the 31.1 tool in charge of the upgrade, which migrates the unit on the way.
>
> Either way, the update after the migration is the first that hot swaps. Check with `systemctl --user show -p Type urnetwork.service`.

> [!NOTE]
> Nodes still on v3.23.0-fix.30.9 have the version-reporting gap described in the 31.0 notes. Verify the result with `urnet-tools version` rather than the exit status of `urnet-tools update`.

### Known Limits

- **HotSwap is not available on Windows.** Updates there restart the provider.
- **A HotSwap candidate can land metrics on a different port.** When a persisted `metrics on` is re-applied after a handoff, the retiring process may still hold its port, so the new process takes the next free port in `127.0.0.1:9100` to `9103`. Set `URNETWORK_METRICS` to pin the address.
